# @mlagie/sql-connector

[![npm version](https://img.shields.io/npm/v/%40mlagie%2Fsql-connector)](https://www.npmjs.com/package/@mlagie/sql-connector)
[![npm downloads](https://img.shields.io/npm/dm/%40mlagie%2Fsql-connector)](https://www.npmjs.com/package/@mlagie/sql-connector)
[![license](https://img.shields.io/github/license/mlagie/sql-connector)](https://github.com/mlagie/sql-connector/blob/main/LICENSE)

A small, typed and dialect-aware SQL layer for **MySQL** and **PostgreSQL**.

`@mlagie/sql-connector` provides:

- connection management;
- declarative table schemas;
- SQL type aliases and native SQL types;
- CRUD operations through models;
- structured `WHERE` / `HAVING` conditions;
- `IN`, `BETWEEN`, `LIKE`, `ILIKE`, `NULL`, `AND`, `OR` and `NOT` conditions;
- aggregations, grouping, ordering and joins;
- foreign-key dependency ordering;
- schema synchronization;
- migration planning, approval, execution and status tracking;
- migration checksums, encrypted migration files and optional encrypted backups;
- TypeScript declarations for the public API.

> **Supported database engines:** MySQL and PostgreSQL.
>
> SQL generated by the connector is dialect-specific where necessary. The schema API stays the same across supported engines.

```bash
npm install @mlagie/sql-connector
```

The package includes both MySQL (`mysql2`) and PostgreSQL (`pg`) drivers.

## Quick start

```js
const {
  Schema,
  Model,
  connect,
  logout,
} = require('@mlagie/sql-connector');

await connect({
  host: 'localhost',
  port: 3306,
  user: 'root',
  password: 'password',
  database: 'mydatabase',
});

const userSchema = new Schema({
  id: {
    type: Number,
    auto_increment: true,
    primary_key: true,
  },
  email: {
    type: String,
    length: 255,
    required: true,
    unique: true,
  },
  status: {
    type: String,
    enum: ['active', 'inactive', 'pending'],
    default: 'pending',
  },
});

const User = new Model('users', userSchema);

await Model.syncAllTables();
await User.save({ email: 'user@example.com', status: 'active' });

const users = await User.find({
  where: {
    status: { IN: ['active', 'pending'] },
  },
});

console.log(users);

await logout();
```

For migrations, use the same models as the desired schema:

```js
const { Migration } = require('@mlagie/sql-connector');

const migration = new Migration({
  encryptionKey: process.env.SQL_CONNECTOR_MIGRATION_KEY,
});

const plan = await migration.plan({ name: 'sync-users' });

if (plan.hasChanges()) {
  plan.approve();
  await plan.execute();
}
```

## Connection

### MySQL

MySQL is the default dialect.

```js
await connect({
  host: 'localhost',
  port: 3306,
  user: 'root',
  password: 'password',
  database: 'mydatabase',
});
```

### PostgreSQL

Pass `postgres` as the second argument.

```js
await connect({
  host: 'localhost',
  port: 5432,
  user: 'postgres',
  password: 'password',
  database: 'mydatabase',
}, 'postgres');
```

### Close the connection

```js
await logout();
```

## Schemas

`Schema` describes the desired structure of a SQL table. A field may be declared with a JavaScript constructor, a SQL-connector type alias, or an object containing a type name.

```js
const schema = new Schema({
  name: { type: String, length: 120, required: true },
  age: { type: Number },
  active: { type: Boolean, default: true },
});
```

### Schema field options

| Property | Type | Description |
|---|---|---|
| `type` | constructor / string / `{ name }` | Field type. |
| `length` | `number` | Length for length-based types. |
| `precision` | `number` | Decimal precision. |
| `scale` | `number` | Decimal scale. |
| `required` | `boolean` | Adds `NOT NULL`. |
| `default` | any | SQL column default. |
| `unique` | `boolean` | Adds `UNIQUE`. |
| `primary_key` | `boolean` | Adds `PRIMARY KEY`. |
| `auto_increment` | `boolean` | Enables auto-increment / identity behavior depending on dialect. |
| `enum` | `string[]` | Allowed values. |
| `foreignKey` | `string` | Foreign-key target such as `users(id)` or `users.id`. |
| `oldname` | `string` | Existing column name used by migrations to request an explicit rename. |
| `customize` | `string` | Additional SQL definition appended to the column. |

> Do not combine `primary_key: true` and `unique: true` on the same field. A primary key is already unique and non-null.

### Types

`sqlTypeMap` exposes the connector's supported SQL type aliases:

| Alias | SQL type | Typical JavaScript value |
|---|---|---|
| `String` | `VARCHAR` | `string` |
| `Char` | `CHAR` | `string` |
| `Number` | `INT` | `number` |
| `SmallInt` | `SMALLINT` | `number` |
| `BigInt` | `BIGINT` | `number` / `bigint` |
| `Decimal` | `DECIMAL` | `number` / decimal string |
| `Boolean` | `BOOLEAN` | `boolean` |
| `Date` | `DATETIME` | `Date` |
| `DateTime` | `DATETIME` | `Date` |
| `Timestamp` | `TIMESTAMP` | `Date` |
| `Float` | `FLOAT` | `number` |
| `Double` | `DOUBLE` | `number` |
| `Text` | `TEXT` | `string` |
| `Blob` | `BLOB` | `Buffer` / binary data |
| `Binary` | `VARBINARY` | binary data |
| `Uuid` | `CHAR` | `string` |
| `Object` | `JSON` | object |
| `Array` | `VARCHAR` | array / serialized value |
| `Now` | `NOW()` | SQL temporal expression* |
| `CurrentTimestamp` | `CURRENT_TIMESTAMP` | SQL temporal expression* |

For `Now` and `CurrentTimestamp`, the mapped values are SQL expressions/constants and are primarily intended for defaults; they are not storage column types.

Example:

```js
const { sqlTypeMap } = require('@mlagie/sql-connector');

console.log(sqlTypeMap.String);           // VARCHAR
console.log(sqlTypeMap.CurrentTimestamp); // CURRENT_TIMESTAMP
```

The schema API also accepts the JavaScript constructors `String`, `Number`, `Boolean`, `Date`, `Object` and `Array`.

### Length, precision and scale

Length-based types support `length`:

```js
const schema = new Schema({
  code: { type: String, length: 32 },
  fixed_code: { type: 'CHAR', length: 8 },
  binary_code: { type: 'VARBINARY', length: 64 },
});
```

For decimal values:

```js
const schema = new Schema({
  amount: {
    type: 'DECIMAL',
    precision: 12,
    scale: 2,
  },
});
```

### Defaults and values

The `default` property accepts values that the active dialect can format as SQL defaults:

```js
const schema = new Schema({
  active: { type: Boolean, default: true },
  retries: { type: Number, default: 0 },
  note: { type: String, default: 'pending' },
  created_at: { type: Date, default: 'CURRENT_TIMESTAMP' },
  metadata: { type: Object, default: { source: 'api' } },
});
```

Supported default value forms include:

- `null`;
- strings;
- numbers and `bigint` values;
- booleans;
- `Date` instances;
- objects, serialized as JSON text;
- temporal SQL values such as `CURRENT_TIMESTAMP`, `NOW` and `NOW()`;
- functions returning a supported value.

`sqlTypeMap.CurrentTimestamp` can also be used as a semantic constant:

```js
created_at: {
  type: Date,
  default: sqlTypeMap.CurrentTimestamp,
}
```

### Constraints

```js
const schema = new Schema({
  id: {
    type: Number,
    primary_key: true,
    auto_increment: true,
  },
  email: {
    type: String,
    required: true,
    unique: true,
    length: 320,
  },
});
```

The connector supports the schema-level concepts `NOT NULL`, `UNIQUE`, `PRIMARY KEY`, `FOREIGN KEY`, `DEFAULT`, `ENUM`, auto-increment and custom SQL options.

### Foreign keys

```js
const orderSchema = new Schema({
  user_id: {
    type: Number,
    foreignKey: 'users(id)',
  },
  product_id: {
    type: Number,
    foreignKey: 'products.id',
  },
});
```

`Model.syncAllTables()` sorts models according to their foreign-key dependencies. Cyclic dependencies are rejected instead of being silently reordered.

## Models

`Model` represents a database table.

```js
const User = new Model('users', userSchema);
```

### `save`

```js
await User.save({
  email: 'user@example.com',
  status: 'active',
});
```

`save(data)` inserts the supplied fields. Values are sent through driver parameters rather than interpolated into the SQL statement.

### `find`

```js
const users = await User.find({
  select: ['id', 'email', { count: 'id', as: 'total' }],
  where: {
    status: { IN: ['active', 'pending'] },
  },
  groupBy: ['id', 'email'],
  orderBy: [
    { field: 'email', direction: 'ASC' },
  ],
  limit: 50,
  offset: 0,
});
```

Supported options:

| Option | Type | Description |
|---|---|---|
| `select` | `SelectItem[]` | Columns, `SUM`, `COUNT`, `DISTINCT`, date formatting and aliases. |
| `where` | structured condition object | Filters rows. Raw SQL strings are rejected. |
| `groupBy` | array | Columns or date-format expressions. |
| `having` | structured condition object | Filters grouped results. Raw SQL strings are rejected. |
| `orderBy` | array | `{ field, direction }` sorting or string columns. |
| `join` | object | Join configuration. |
| `limit` | integer | Maximum number of rows. `0` is treated as no limit by the current implementation. |
| `offset` | integer | Number of rows to skip. |

### `count`

```js
const total = await User.count({
  status: 'active',
});
```

`count(filter)` returns the number of matching rows.

### `delete`

```js
await User.delete({
  email: 'user@example.com',
});
```

The method returns `1` when rows are affected and `0` otherwise.

### `dropTable`

```js
await User.dropTable();
```

Drops the model table.

### `generate_uuid`

```js
const uuid = await User.generate_uuid();
const customUuid = await User.generate_uuid('custom_uuid');
```

The method asks the active dialect for a UUID, checks uniqueness and returns the generated UUID or `null`.

### `customRequest`

```js
const result = await User.customRequest(
  'SELECT id, email FROM users'
);
```

Use this escape hatch for SQL features not represented by the structured query API. Because the SQL string is executed as supplied, only use trusted SQL here.

## Conditions

Conditions are represented as JavaScript objects. Raw `WHERE` and `HAVING` strings are intentionally rejected by the structured query builder.

### Simple values

```js
{ status: 'active' }
```

Generates a parameterized equality comparison.

Multiple fields are combined with `AND`:

```js
{
  status: 'active',
  role: 'admin',
}
```

### Comparison operators

The supported comparison operators are:

| Operator | Example |
|---|---|
| `=` | `{ age: { '=': 18 } }` |
| `!=` | `{ status: { '!=': 'deleted' } }` |
| `>` | `{ age: { '>': 18 } }` |
| `<` | `{ age: { '<': 65 } }` |
| `>=` | `{ age: { '>=': 18 } }` |
| `<=` | `{ age: { '<=': 65 } }` |
| `LIKE` | `{ email: { LIKE: '%@example.com' } }` |
| `NOT LIKE` | `{ email: { 'NOT LIKE': '%@example.com' } }` |
| `ILIKE` | `{ email: { ILIKE: '%@example.com' } }` |
| `NOT ILIKE` | `{ email: { 'NOT ILIKE': '%@example.com' } }` |
| `IN` | `{ status: { IN: ['active', 'pending'] } }` |
| `NOT IN` | `{ status: { 'NOT IN': ['deleted'] } }` |
| `BETWEEN` | `{ age: { BETWEEN: [18, 65] } }` |
| `NOT BETWEEN` | `{ age: { 'NOT BETWEEN': [18, 65] } }` |

`ILIKE` is native on PostgreSQL. On MySQL it falls back to a case-insensitive `LOWER(column) LIKE LOWER(value)` expression.

### `IN` / `NOT IN`

```js
{
  status: {
    IN: ['active', 'pending'],
  },
}
```

Values are parameterized individually.

```js
{
  status: {
    'NOT IN': ['deleted', 'blocked'],
  },
}
```

Use arrays for these operators. An empty list is not a meaningful SQL `IN` expression and should not be passed.

### `BETWEEN` / `NOT BETWEEN`

```js
{
  created_at: {
    BETWEEN: [
      new Date('2026-01-01'),
      new Date('2026-12-31'),
    ],
  },
}
```

The value must contain exactly two bounds: `[min, max]`.

### `NULL`

A plain `null` value is translated to `IS NULL`:

```js
{ deleted_at: null }
```

Explicit equality and inequality with `null` are normalized as well:

```js
{ deleted_at: { '=': null } }
{ deleted_at: { '!=': null } }
```

These become `IS NULL` and `IS NOT NULL`; no placeholder is consumed for the `NULL` literal.

### `AND` / `OR` / `NOT`

Nested conditions are supported:

```js
{
  AND: [
    { active: true },
    {
      OR: [
        { role: 'admin' },
        { role: 'moderator' },
      ],
    },
  ],
}
```

Negation accepts one structured condition object:

```js
{
  NOT: {
    status: { IN: ['deleted', 'blocked'] },
  },
}
```

Empty `AND` / `OR` arrays and invalid `NOT` values are rejected.

## Select, aggregation, grouping and ordering

### Select items

A `select` entry can be a column string or a structured object.

| Form | Meaning |
|---|---|
| `'email'` | Select a column. |
| `'*'` | Select all columns. |
| `{ col: 'email', as: 'address' }` | Column with alias. |
| `{ sum: 'amount', as: 'total' }` | `SUM(amount)`. |
| `{ count: 'id', as: 'total' }` | `COUNT(id)`. |
| `{ count: ['team', 'source'], as: 'groups' }` | Multi-column count expression. |
| `{ count: { status: 'active' }, as: 'active' }` | Conditional count expression. |
| `{ distinct: 'status' }` | `DISTINCT status`. |
| `{ dateFormat: ['created_at', '%Y-%m'], as: 'period' }` | Formatted date expression. |

Example de sélection et d'agrégation :

```js
const stats = await User.find({
  select: [
    'status',
    { count: 'id', as: 'total' },
    { sum: 'amount', as: 'revenue' },
  ],
  where: {
    active: true,
  },
});
```

### Groupement avec `GROUP BY`

`groupBy` s'utilise directement dans les options de `find()`. Il doit correspondre aux colonnes ou expressions qui définissent chaque groupe.

```js
const stats = await User.find({
  select: [
    'status',
    { count: 'id', as: 'total' },
    { sum: 'amount', as: 'revenue' },
  ],
  groupBy: ['status'],
});
```

Un élément de `groupBy` peut être une colonne (`'status'`) ou une expression structurée telle que `dateFormat`.

### Filtrer les groupes avec `HAVING`

`having` s'applique **après** le groupement et utilise exactement le même format de conditions structurées que `where`. Par exemple, pour conserver uniquement les groupes contenant plus de 10 lignes :

```js
const stats = await User.find({
  select: [
    'status',
    { count: 'id', as: 'total' },
  ],
  groupBy: ['status'],
  having: {
    total: { '>': 10 },
  },
});
```

Les chaînes SQL brutes dans `having` sont refusées par le query builder.

### Tri avec `ORDER BY`

`orderBy` s'ajoute aux mêmes options et permet de trier le résultat final. Il peut notamment trier sur une colonne sélectionnée ou sur un alias d'agrégation :

```js
const stats = await User.find({
  select: [
    'status',
    { count: 'id', as: 'total' },
  ],
  groupBy: ['status'],
  having: {
    total: { '>': 10 },
  },
  orderBy: [
    { field: 'total', direction: 'DESC' },
    { field: 'status', direction: 'ASC' },
  ],
});
```

Seules les directions `ASC` et `DESC` sont acceptées.

### Exemple complet : `SELECT` + agrégation + `WHERE` + `GROUP BY` + `HAVING` + `ORDER BY`

L'exemple suivant montre comment toutes ces clauses se combinent dans une seule requête :

```js
const stats = await User.find({
  select: [
    'status',
    { count: 'id', as: 'total' },
    { sum: 'amount', as: 'revenue' },
  ],
  where: {
    active: true,
  },
  groupBy: ['status'],
  having: {
    total: { '>': 10 },
  },
  orderBy: [
    { field: 'total', direction: 'DESC' },
  ],
});
```

Conceptuellement, cette configuration correspond à :

```sql
SELECT status, COUNT(id) AS total, SUM(amount) AS revenue
FROM users
WHERE active = ?
GROUP BY status
HAVING total > ?
ORDER BY total DESC
```

Les valeurs de `WHERE` et `HAVING` restent paramétrées par le Connector.

## Joins

The current model API exposes an `INNER JOIN` configuration through `find`:

```js
const rows = await User.find({
  select: [
    { col: 'users.email', as: 'email' },
    { col: 'profiles.display_name', as: 'name' },
  ],
  join: {
    table: 'profiles',
    on: 'users.id = profiles.user_id',
  },
});
```

The query builder also documents `JoinOption` shapes with `alias` and `type`; however, the current `Model.find()` implementation builds the join from `table` and `on` and emits `INNER JOIN`. Do not rely on `LEFT` / `RIGHT` behavior until the model layer exposes those options end-to-end.

## Schema synchronization

`Model.syncAllTables()` creates model tables in foreign-key dependency order.

```js
await Model.syncAllTables();
```

It handles:

- table creation;
- multiple foreign keys;
- dependency ordering;
- cyclic dependency detection.

For controlled schema evolution, prefer the migration API described below.

## Migrations

The migration subsystem compares the **desired schema from your models** with the **actual database schema**, creates a migration plan, and can execute the resulting DDL.

Migration components are exposed from the package root:

```js
const {
  Migration,
  MigrationPlan,
  MigrationStore,
  MigrationRunner,
  SchemaDiffer,
  SchemaInspector,
  MySQLDialect,
  PostgreSQLDialect,
  MigrationError,
  DestructiveMigrationError,
  MigrationChecksumError,
} = require('@mlagie/sql-connector');
```

### Migration workflow

The recommended workflow is:

```text
Model schemas
    │
    ▼
Migration.plan()
    │
    ├── inspect current database
    ├── build desired snapshot
    ├── calculate schema differences
    └── generate dialect-specific SQL
    │
    ▼
MigrationPlan
    │
    ├── inspect changes
    ├── approve()
    └── execute()
    │
    ▼
Database + migration history + snapshot
```

Basic usage:

```js
const migration = new Migration({
  encryptionKey: process.env.SQL_CONNECTOR_MIGRATION_KEY,
});

const plan = await migration.plan({
  name: 'users-schema',
});

console.log(plan.toJSON());

if (plan.hasChanges()) {
  plan.approve();
  await plan.execute();
}
```

Or use the convenience method:

```js
await Migration.migrate({
  name: 'users-schema',
  encryptionKey: process.env.SQL_CONNECTOR_MIGRATION_KEY,
});
```

### Migration options

`Migration` accepts:

| Option | Type | Description |
|---|---|---|
| `connection` | driver connection | Existing database connection. Defaults to the active connector connection. |
| `dialect` | `'mysql' \| 'postgres'` / dialect instance | Database dialect. Defaults to the active connector dialect. |
| `models` | `Model[]` | Explicit models to compare. Defaults to pending models. |
| `directory` | `string` | Migration storage directory. Default: `migrations`. |
| `backupDirectory` | `string` | Encrypted backup directory. |
| `encryptionKey` | `string` | Secret used for migration and backup encryption. |
| `retention` | number / duration string | Backup retention. Supports `ms`, `s`, `m`, `h`, `d`, `w`. |
| `allowDestructiveChanges` | `boolean` | Allows column drops. |
| `allowDropTables` | `boolean` | Allows table drops. |

Examples:

```js
new Migration({
  directory: './database/migrations',
  backupDirectory: './database/backups',
  encryptionKey: process.env.SQL_CONNECTOR_MIGRATION_KEY,
  retention: '30d',
});
```

### Migration plans

`Migration.plan()` returns a `MigrationPlan`.

```js
const plan = await migration.plan({
  id: '20260915_add_status',
  name: 'add status',
});
```

Available methods:

| Method | Description |
|---|---|
| `hasChanges()` | Returns whether operations are pending. |
| `hasDestructiveChanges()` | Returns whether destructive operations are present. |
| `destructiveChanges()` | Returns destructive operations. |
| `approve()` | Marks the plan as approved. |
| `execute(options)` | Executes the attached plan. |
| `toJSON()` | Returns a serializable plan representation. |

A plan exposes:

- `id`;
- `dialect`;
- `checksum`;
- `operations`;
- generated `sql`;
- desired `snapshot`;
- previous/current baseline snapshot.

### Detected migration operations

The schema differ can generate:

| Operation | Meaning | Destructive |
|---|---|---:|
| `createTable` | Creates a missing table. | No |
| `addColumn` | Adds a missing column. | No |
| `renameColumn` | Renames a column declared with `oldname`. | No |
| `alterColumn` | Changes a column definition. | No |
| `dropColumn` | Removes a column absent from the desired schema. | Yes |
| `dropTable` | Removes a table absent from the desired schema. | Yes |

Renames are explicit. The differ does not guess that two similarly named columns are the same column.

Example:

```js
const schema = new Schema({
  email_address: {
    type: String,
    length: 320,
    oldname: 'email',
  },
});
```

This can produce a `renameColumn` operation from `email` to `email_address`, followed by an `alterColumn` if the definition also changed.

### Destructive changes

Column and table removal require explicit authorization.

```js
const plan = await migration.plan({
  allowDestructiveChanges: true,
  allowDropTables: true,
});

if (plan.hasDestructiveChanges()) {
  console.warn(plan.destructiveChanges());
}

plan.approve();
await plan.execute({
  allowDestructiveChanges: true,
});
```

Approval and destructive-change authorization are separate safeguards.

### Checksums

Every generated migration receives a SHA-256 checksum derived from its migration id, dialect, operations and generated SQL.

The migration history table is named `sql_connector_migrations`.

If an already-applied migration id is found with a different checksum, execution stops instead of silently accepting the mismatch.

### Encrypted files

Migration SQL is stored as encrypted `.sql.enc` files.

Set the key through the constructor:

```js
const migration = new Migration({
  encryptionKey: process.env.SQL_CONNECTOR_MIGRATION_KEY,
});
```

Or through the environment:

```bash
export SQL_CONNECTOR_MIGRATION_KEY='a-long-random-secret'
```

The encryption format uses AES-256-GCM with a derived key. Migration files are written with restrictive filesystem permissions.

> Never commit `SQL_CONNECTOR_MIGRATION_KEY` or plaintext secrets to source control.

### Backups and retention

If `retention` is configured, affected tables are backed up before migration execution and written as encrypted JSON files.

```js
const migration = new Migration({
  encryptionKey: process.env.SQL_CONNECTOR_MIGRATION_KEY,
  retention: '30d',
});
```

Accepted duration units:

- `ms`: millisecond
- `s`: seconde
- `m`: minute
- `h`: heure
- `d`: jour
- `w`: semaine

`Migration.cleanup()` removes expired backup files.

Backups are currently data-oriented snapshots. The connector does not automatically restore them.

### Migration status

```js
const migration = new Migration();
const status = await migration.status();
console.table(status);
```

The migration runner maintains the database-side history table and can also inspect the stored migration files.

## Model instances

Queries return `ModelInstance` objects.

```js
const [user] = await User.find({
  where: { email: 'user@example.com' },
});

await user.updateOne({ status: 'inactive' });
await user.delete();
```

Available methods include:

- `updateOne(data)`;
- `delete(filter?)`;
- `customRequest(sql)`;
- `getRecordData()`;
- `toJSON()`.

When a model schema contains primary-key fields, `updateOne()` uses those primary-key values to target the row when possible.

## Security and SQL safety

The structured query builder is designed to keep identifiers and values separate.

- `WHERE` values are parameterized.
- `HAVING` values are parameterized.
- `IN` / `NOT IN` values are parameterized individually.
- `BETWEEN` bounds are parameterized individually.
- PostgreSQL placeholders are generated as `$1`, `$2`, etc.
- MySQL uses `?` placeholders.
- Identifiers are validated before dialect-specific escaping.
- Raw `WHERE` / `HAVING` strings are rejected by the structured builder.

`customRequest()` is intentionally outside that protection because it accepts raw SQL. Use it only with trusted query text.

---

## Dialect matrix

| Feature | MySQL | PostgreSQL |
|---|---|---|
| Connection driver | `mysql2` | `pg` |
| Identifier quotes | backticks | double quotes |
| Parameter placeholders | `?` | `$1`, `$2`, ... |
| Boolean SQL literals | `1` / `0` | `TRUE` / `FALSE` |
| UUID query | `UUID()` | `gen_random_uuid()` |
| Transactional DDL | engine-dependent | supported by migration dialect |

The migration dialect layer is separate from the query dialect layer so schema DDL and runtime queries can evolve independently.
