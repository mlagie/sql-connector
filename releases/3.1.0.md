# Analysis of the 3.1.0 release notes

## General observation

The 3.1.0 release notes heavily mix content that has **existed for a long time** with what is actually new, without ever distinguishing between the two. A reader who has been following releases since the 2.x line would think they're being told about brand-new features they've actually been using for months.

---

## Presented as "new" but already existing for several versions

|                       Section in 3.1.0                                |                                                                        Reality                                                                          |
|-----------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------|
| Section 2 "More WHERE Conditions" (`=, !=, >, <, LIKE, IN, BETWEEN…`) | Already implemented in `buildQuery.js` (`COMPARISON_OPERATORS`), already documented in `QUERY.md` and the README well before 3.1.0                      |
| Section 3 IN/NOT IN, Section 4 BETWEEN, Section 5 AND/OR/NOT          | Present in `buildWhere()` since at least v2.2.0 (the 2.2.0 changelog already introduces `AND`/`OR` with the same "cannot be empty" errors)              |
| Section 6 NULL                                                        | Fixed in **3.0.2**, not new in 3.1.0                                                                                                                    |
| Section 7-13 SELECT, COUNT, SUM, GROUP BY, HAVING, ORDER BY           | Have existed since **1.5.0** (query builder) and **2.0.5 / 2.0.7** (polymorphic COUNT, automatic alias). `buildQuery.js` hasn't changed on these points |
| Section 1 "Expanded SQL Data Types"                                   | List **identical** to the current `sqlTypeMap.js`, which itself hasn't changed — no new type was added                                                  |

---

## What actually seems new

Sections **20 to 27** (plan generation, execution, naming, reviewing changes, destructive-change detection, approval, status, cleanup) are likely the real novelty of this release: the migration workflow.

Problem: nothing in the text signals this explicitly. It's buried in the middle of everything else as if it all carried equal weight.

---

## Documented items that don't match the code

This is the most concerning point: some examples in the notes wouldn't actually work as written.

1. **`<>` as an operator** (Section 2, list of operators)
   Doesn't exist in `COMPARISON_OPERATORS` (`buildQuery.js`). Only `!=` is supported.

2. **`references: { table, column, onDelete }`** (Section 19, "Structured references")
   Doesn't exist anywhere in the code. `Model.js`, `SchemaSnapshot.js` and `SchemaDiffer.js` only recognize `foreignKey: 'table(col)'` or `'table.col'`. If a developer uses this example, the field would simply be ignored, with no error.

3. **`Migration.cleanup({ retention: "7d" })`** (Section 27)
   The actual signature is `Migration.cleanup()`, with no arguments. `retention` is only configured at the construction of `Migration` / `MigrationStore`. The given example is therefore incorrect.

---

## Recommendations

- Rewrite the notes to keep only what **actually changed** since 3.0.4 (most likely: the migration system, if this is indeed its first official exposure/documentation, plus nothing else on the query-builder side).
- Either remove sections 1 through 19 entirely (recap of already-existing features), or move them to a separate appendix such as **"Existing API recap"**, clearly distinguished from **"New in this version"**.
- Fix or remove the 3 examples that don't match the code (`<>`, `references`, `Migration.cleanup(options)`), to avoid documenting an API that doesn't exist.
